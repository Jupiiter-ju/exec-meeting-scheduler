# Exec Meeting Scheduler

Executive meeting booking system for internal team use. Repo: github.com/Jupiiter-ju/exec-meeting-scheduler

## Architecture

Three pieces, all driven by one shared n8n backend workflow:

1. **Website** (`index.html`) — single-file HTML/CSS/JS, no build step. Calls the n8n webhook directly via `fetch`. The only file tracked in this git repo.
2. **Discord bot** ("น้องจู" / Agent-Ju) — an n8n AI Agent node (Google Gemini model) that talks to users in Discord DMs and calls the same backend via tool nodes (`check_availability`, `book_meeting`, `book_multi_meeting`, `find_my_meeting`, `cancel_meeting`, `cancel_batch_meeting`).
3. **n8n backend workflow** — not stored in this repo (n8n has no direct API access from this environment). Writes to Google Calendar and logs to Google Sheets. The user exports/pastes node code manually when it needs inspecting or editing (see workflow note below).

4. **Meeting reminder** (`apps-script/reminder.gs`) — **Google Apps Script, not n8n, since 2026-10-22.** A 10-minute time-driven trigger reads the 3 calendars (Calendar advanced service, falls back to CalendarApp), finds events starting ~1 h ahead (50–70 min window + 30 min catch-up), parses `ผู้ขอนัด:` / `หัวข้อ:` / `ผู้บริหารที่เข้าร่วม:` from the description, maps the caller name to a Discord ID and DMs them via the Discord REST API (open DM channel → post message). Dedupe is a `REMINDED_KEYS` map in Script Properties keyed `start|summary` (so a "both" booking's 2 events remind once), pruned after 36 h. Secrets and the name→ID map live only in Script Properties (`DISCORD_BOT_TOKEN`, `NAME_TO_DISCORD`, optional `EXCLUDE_NAMES`, `TEST_DISCORD_ID`); `apps-script/make_name_map.js` regenerates the map JSON from `Resolve Employee` in the main export into the gitignored `name_map.local.json`. Setup/test guide: `apps-script/README.md` (Thai). **The n8n workflow "แจ้งเตือนนัดหมายล่วงหน้า 1 ชม. (Meeting Reminder)" is retired** — it must stay inactive (or be deleted) or users get double DMs; `Meeting Reminder 1h.json` is kept only as the historical source. When adding an employee, update both `Resolve Employee` (n8n) and the `NAME_TO_DISCORD` property (re-run `make_name_map.js`). **Decided 2026-10-27: Discord DM is the only reminder channel** — do not turn on Google Calendar's own email notifications on the 3 calendars; don't re-propose it.

5. **First-contact broadcast** (n8n workflow "Exec Meeting - Discord First Contact Broadcast", export `Exec Meeting - Discord First Contact Broadcast.json`, untracked) — a **manual** workflow (Manual Trigger → `Recipient List` Code node with a hardcoded `RECIPIENTS` array → Loop Over Items → `Discord: Send Introduction DM` → Wait 1.5 s). `active: false` is normal for it. It is run by hand once per new employee to DM them น้องจู's intro message + the website link. **Onboarding checklist for a new employee (3 places):** (1) add them to `EMPLOYEE_MAP` in `Resolve Employee` (main workflow) or the bot refuses them; (2) refresh the Apps Script reminder's `NAME_TO_DISCORD` property (`apps-script/make_name_map.js`); (3) edit `Recipient List` to contain *only* the new person(s) and click Test workflow — leftover names get the intro again. `n8n-discord-broadcast-workflow.json` in the project root is an older copy of the same idea. Could move into the Apps Script project later (same bot token, same DM code) but is not worth it while the bot itself stays on n8n.

### Data stores
- **Google Calendar**, 3 calendars: `exe` (คุณกฤช), `combo` (คุณเบียร์), `agenix` (Agenix/AGX company bookings always land here regardless of which exec).
- **Google Sheet "Record Appointments Exec - Bot"**, tabs:
  - `ChatLog` — every Discord message + bot reply, logged for debugging.
  - `BookingLog` — booking records with a `Status` column (Active/Cancelled) kept in sync by a separate scheduled workflow.
  - `AddressBook` (added 2026-09) — nickname → email lookup for auto-inviting meeting participants by email. Columns are English (`Nickname`, `Email`) because Thai text cannot be typed into Google Sheets' canvas grid via browser automation (see Gotchas).

### Identity model
- Discord bot: `Resolve Employee` node maps the message's real Discord `authorId` to a name/email/company via a hardcoded `EMPLOYEE_MAP` in code — the AI can never impersonate another user because `callerName`/`requesterEmail` sent to every backend tool call are hardcoded n8n expressions (`{{ $('Resolve Employee').item.json.employeeName }}`), not model-fillable fields.
- Backend authorization for cancel/find matches by checking whether the caller's own name/email appears anywhere in the target event's description (organizer *or* participant — not restricted to "the person who booked it").
- Website: caller name/email come straight from the form, no Discord identity involved. A `source: 'website'` field is included on every website webhook payload specifically so backend logic can special-case website vs. Discord behavior.

## Workflow rules (apply every session, no need to re-ask)

- **Respond in Thai.**
- **`index.html` changes**: commit and push straight to `master` (no feature-branch step). Always syntax-check first:
  ```
  node -e "const fs=require('fs'); const html=fs.readFileSync('index.html','utf8'); const m=html.match(/<script>([\s\S]*)<\/script>/); new Function(m[1]); console.log('OK');"
  ```
- **n8n backend changes**: no direct access. Give the user exact copy-paste code (old string → new string, or full node body) for them to paste into the node themselves; they paste the result back for verification. Never assume a change landed without seeing it pasted back.
- **Verify against the workflow export before trusting status notes in this file.** The user keeps a full n8n export at `Exec Meeting Scheduler V.1.json` in the project root (untracked — contains employee emails/Discord IDs, don't commit it). Several "done"/"in progress" claims below turned out wrong when checked against it on 2026-10-15. Ask the user to re-export (overwrite that file) and inspect it with `node` (parse the JSON, find the node by name, read `parameters.jsCode` / `onError` / `parameters.options.systemMessage`) before relying on any claim about current node state.
- **Prefer additive, narrowly-scoped changes** to backend nodes — this system is in active production use (real people booking real meetings with executives). A shared node feeding every action branch (e.g. inserting a lookup node between the webhook trigger and the router) can take down the *entire* bot if it errors, not just the feature being added. Test new nodes in isolation (Execute Step with pinned/mock data) before wiring them into the live path.
- **Google Sheets cannot be edited via browser automation** — neither the in-app browser nor Claude in Chrome can type into Sheets' canvas-rendered grid (keystrokes silently don't register; this is not an auth issue, confirmed by testing on a fresh session in real Chrome too). Ask the user to type Sheet edits themselves.

## Known gotchas (already root-caused once — don't re-diagnose from scratch)

- **Mobile Thai IME breaks if you reassign `el.value` on every `input` event.** Any live-filtering input handler (e.g. Thai-only character enforcement) must skip filtering while `compositionstart`/`compositionend` is in progress, or mobile keyboards can't type multi-character Thai words into the field at all.
- **Split participant/name lists on `/[,\s]+/`, not just `,`.** Users often separate names with a space instead of a comma; nobody's nickname in this system contains an internal space, so splitting on either is safe and prevents "two names glued together" bugs.
- **Normalize Thai strings with `.normalize('NFC')` before comparing for equality.** Text typed on different devices/keyboards can encode the same visible string with different Unicode composition, breaking naive `===`/`.includes()` dedup checks (this caused a name to be duplicated in event titles).
- **The AI Agent occasionally returns a genuinely empty `output` with no tool call**, even though the n8n execution shows "Succeeded" — Discord then shows the hardcoded fallback from `Discord: ตอบกลับ`'s `content` field ("ขอโทษค่ะ ระบบขัดข้องชั่วคราว รบกวนพิมพ์คำสั่งเดิมซ้ำอีกครั้งได้ไหมคะ..."), and retyping the confirmation word doesn't help — same failure repeats. Confirmed via Executions → AI Agent node → Logs → `Google Gemini Chat Model` sub-step → Output → **JSON** view: `finishReason: "STOP"` with `completionTokens: 0` (promptTokens ~9,140 — not near any token ceiling, so **not** a `MAX_TOKENS` truncation, and no `promptFeedback.blockReason` either, so **not** a safety-filter block). An identical-looking booking (same confirm step, same shape) from a different user succeeded seconds apart, confirming this is a genuinely random/intermittent empty-response glitch on Gemini's side, not something triggered deterministically by our prompt/tool setup.
  - **2026-09 mitigation tried, then reverted — see next gotcha below**: briefly changed the `Window Buffer Memory` session `Key` to reset daily. This introduced a much worse bug (AI hallucinating a fake booking with fabricated details when memory reset mid-conversation) and was reverted. `contextWindowLength` was unrelated to the incident (the live value is **8** as of the 2026-10-15 export, not 10 as previously noted here) and the `Key` is back to plain `={{ $('Resolve Employee').item.json.authorId }}`. **Net effect: this glitch stayed unmitigated until the retry path went live on 2026-10-22 (see below)** — it was confirmed recurring on 2026-09-11/12 (same `finishReason: STOP` / `completionTokens: 0` signature, ~10,331 prompt tokens, very short conversation — so it really is random, not context-size-driven).
  - **Auto-retry path: BUILT and live since 2026-10-22** (verified against the 2026-10-22 14:56 export, 73 nodes, and an Executions run). Wiring: `AI Agent` → `Output ว่างไหม?` (IF v2.3, string "is empty" on `{{ ($json.output || '').toString().trim() }}`, combinator left at `or` — harmless with one condition) → **false** → `Discord: ตอบกลับ` + `Log Chat` (the normal path, unchanged); **true** → `AI Agent (Retry)` → the same two nodes. `AI Agent (Retry)` is a copy of `AI Agent` (Tools Agent v1.7, identical 30 KB systemMessage) except `text` = `{{ $('Resolve Employee').item.json.message }}` and all 11 `$json.xxx` in the systemMessage rewritten to `$('Resolve Employee').item.json.xxx` (Resolve Employee rather than รู้จักไหม — same data, and it is what `Discord: ตอบกลับ`/`Log Chat` already use). It **shares** the existing `Google Gemini Chat Model`, `Window Buffer Memory` and all 6 tool nodes (each sub-node now has two output connections), so a tool-body fix applies to both agents automatically — never duplicate the tool nodes. Verified: the IF routed a mock `{output:""}` to true and `{output:"สวัสดี"}` to false (temporary Set node, deleted); the retry agent was exercised live through a temporary second IF condition (message contains `RETRYTEST`, removed afterwards) — execution 2026-10-22 14:52:24 ran AI Agent → IF → AI Agent (Retry) → `find_my_meeting` → Discord reply in correct Thai with the correct caller name; after cleanup a plain "สวัสดีจ้า" DM (15:09) went through the false branch normally and its ChatLog row has no `[retry]` prefix. `Log Chat`'s `คำตอบบอท` is now `{{ ($('AI Agent (Retry)').isExecuted ? '[retry] ' : '') + ($json.output || '') }}`, so ChatLog rows starting with `[retry] ` measure how often the glitch fires. If the retry also returns empty, `Discord: ตอบกลับ`'s hardcoded fallback still applies. Known caveat: the first (empty) exchange is saved to `Window Buffer Memory` before the retry runs, so the retry sees one empty assistant turn in history. **Build lesson**: pasting node JSON that contains Thai via Notepad on this Thai-locale machine garbled every Thai character (UTF-8 bytes read as cp874, `สำคัญ` → `เธชเธณเธ„เธฑเธ`) — the pasted systemMessage was 80 KB of mojibake while the node *name* looked fine on the canvas; always diff pasted Thai against the export (`sm === expected`) instead of trusting the canvas, and hand long Thai text over inside the chat (code block) or via `Set-Clipboard`, not as a file to open.
  - **Planned, not started (2026-09-15): friendly "busy" reply on Gemini rate limits.** Set `AI Agent` → On Error: Continue, add an IF after it matching `/429|RESOURCE_EXHAUSTED|rate limit|quota/i` on `$json.error`, and route matches to a fixed reply ("น้องจูกำลังคุยกับหลายคนพร้อมกันอยู่ รบกวนรอสักครู่แล้วลองใหม่นะคะ") → `Discord: ตอบกลับ`. Step 0 is to capture a real 429 error's shape from Executions first — it has never been observed, so the IF condition is a guess until then. Chosen over a homemade concurrency counter, which would sit on the shared entry path every message passes through.
- **A session key that resets on calendar-day boundaries can wipe conversation memory *mid-conversation*, not just between days.** Discovered 2026-09-12: the `Window Buffer Memory` session key `authorId + '_' + todayDate` (tried as a mitigation for the empty-output glitch above) meant a conversation still in progress right at midnight got a *different* memory key on the very next message — the AI received just "ยืนยัน" with zero prior context (no `message`/summary history at all), and instead of asking what was being confirmed, it **fabricated an entire fake booking** (wrong date count — 1 day instead of the requested 4 — wrong time, wrong topic, an invented participant name never mentioned) and told the user it succeeded. Nothing was actually created on the calendar. Reverted the session key back to plain `authorId` (see mitigation note above) and added system-prompt rule 4.2: if the latest message is a bare confirmation word but there's no prior bullet-point summary in memory to confirm, the AI must say it's unsure what's being confirmed and ask again from scratch — never fabricate. **Takeaway: never key session/conversation memory to a value that can change while a conversation is actively open** (calendar date, calendar week, etc.) — key it to something stable for the conversation's lifetime, or add explicit re-confirmation logic if resets are needed.
- **n8n node renames are safe** — renaming via the UI (double-click the node title) auto-updates every `$('OldName')` expression reference elsewhere in the workflow. Router/Switch nodes in particular are never referenced by name downstream, so renaming them is essentially risk-free.
- **Batch/package booking (`book_multi`, website "นัดหมายเป็นชุด") could silently drop trailing dates with zero error shown.** Reported case: booked every Tuesday from 1 ก.ย. to 29 ธ.ค. 2569 (16 bookable days after 1 holiday excluded) — the confirmation page showed "จองสำเร็จ 5/5 วัน" and listed only the 5 September Tuesdays; October–December (12 days) vanished from *both* the "booked" and "จองไม่สำเร็จ" lists, with no error surfaced anywhere. Root cause not confirmed with execution logs (too old to find by the time it was reported — **check Executions soon after a report like this, they age out**). Leading theory: `Create Event (Multi)` calls Google Calendar once per date sequentially; if one call errors partway through and the node's `On Error` was left at the n8n default (`Stop Workflow`), items after the failure point never reach `Aggregate Multi Results` at all — they aren't recorded as booked *or* failed, they just never get processed.
  - **Fix**: `Aggregate Multi Results` checks each item for `.json.error` and routes those into `failed` (merged with `decide.conflicts`) — in place since 2026-09. **But the other half — `Create Event (Multi)` Settings → On Error: "Continue" — was recorded here as done in 2026-09 and was actually never applied**; the 2026-10-15 export showed it still at the default (Stop Workflow), so until then any single failed date still aborted the whole batch and the error handling in `Aggregate Multi Results` was dead code. **Applied and verified against the export on 2026-10-15** (`onError: continueRegularOutput`, same as `Create Event`). It must be plain "Continue", not "Continue (using error output)", because `Aggregate Multi Results` reads errors from the regular output.
  - If this resurfaces, check the execution **immediately** (Executions → `Create Event (Multi)` node → compare input vs output item count, look for a red/error item) before it ages out of the retention window.
- **`book_multi_meeting`/`book_multi` (recurring multi-day booking, both Discord and website) fails outright for date ranges spanning more than ~90-100 days**, with Google Calendar's `freebusy.query` returning `400 Bad Request — "The requested time range is too long."` at the `FreeBusy Query (Multi)` node (confirmed 2026-09-11, e.g. a 105-day Mon-only recurring request from 14 ก.ย. to 28 ธ.ค. 2569). Google's exact undocumented cutoff is somewhere below 105 days — guessing at a safe threshold and rejecting longer requests with a friendlier error (tried 90, then 120 days) still failed once the real request landed below the guessed cap but above Google's actual one, so **don't reintroduce a day-count guess for this**.
  - **2026-09-12 fix (the real one — no more guessing)**: `Build Multi FreeBusy Request` now splits `minDate`–`maxDate` into 30-day chunks and returns **multiple items** (one per chunk) instead of one big request; `FreeBusy Query (Multi)` (an HTTP Request node) automatically fires once per item; `Compute Multi Availability & Decide` now reads `$input.all()` and merges the `busy` arrays from every chunk before computing conflicts, instead of `$input.first()`. The day-span validation error that was added to `Expand Recurring Dates` as a stopgap was removed — no longer needed. Confirmed working live via Discord for a 4-week recurring booking (2026-09-12); **a 100+ day request has not been re-tested yet** but uses the same chunking logic so is expected to work.
- **Concurrent bookings for the exact same slot could all succeed — confirmed by deliberate load testing (2026-09-14), not a hypothetical.** Fired 10 concurrent `action: "book"` requests straight at the production webhook (bypassing Discord/website) for the identical date+time+exec; **all 10 returned `success: true` with 10 distinct event IDs** — Google Calendar ended up with 10 duplicate events for one slot. Root cause: classic TOCTOU — `Check Conflict`'s freebusy read happens before any of the racing requests has created its event, so every one of them sees the slot as free. A second load-test run (10 concurrent requests to 10 *different* slots) completed cleanly with consistent ~5s response times — the backend has no problem with concurrent *volume*, only with concurrent writes to the *same* slot. (Note: this load test only exercised the webhook/backend directly — it says nothing about Gemini's or Discord's own rate limits if many real users message the bot at once; that layer has not been load-tested.)
  - **2026-09-14 fix**: give every created event a **deterministic ID** derived from `calendarId|date|start` (a small dependency-free hash → `Number.toString(32)`, whose output alphabet (`0-9a-v`) already matches what Google Calendar IDs allow — no `crypto` module needed, which may not be allowlisted in this self-hosted n8n anyway). Two racing requests for the same slot now compute the *same* ID, so Google Calendar itself rejects the second `events.insert` with `409` — true atomicity from Google's backend, no custom locking required. Added to both `Build FreeBusy Request (Book Guard)` (single-day) and `Compute Multi Availability & Decide` (multi-day, in the `toBook.push(...)` event bodies). `Create Event`'s node Settings → **On Error: Continue** so a losing request's `409` doesn't abort the whole execution; `Aggregate Multi Results` already had a per-item `.error` check from the earlier batch-booking fix — but on the multi-day path that check only works with `Create Event (Multi)` set to On Error: Continue, which wasn't actually applied until 2026-10-15 (see the batch-booking gotcha above). Until then a losing multi-day `409` stopped the workflow instead of being reported as a failed date.
  - **Correction (2026-09-14, after reading the actual node body — the line above overstated it)**: `Respond Booked`'s real logic is just `if (items.length === 1 && items[0].json.error) return { success: false, error: items[0].json.error }` — it passes Google Calendar's **raw API error string straight through**, with no `otherAvailableSlots` and no friendly "just got booked" rewrite. That polished conflict message (system-prompt rule 5.1: "แจ้งว่าช่วงเวลาที่ขอเพิ่งถูกจองไปแล้ว...พร้อม `otherAvailableSlots`") only fires on the *ordinary* conflict path — a slot `check_availability` already knew was busy before booking was attempted — not on this race-condition path, where the slot looked free at check time and only failed at the actual `events.insert`. So the loser of a real race currently gets a raw, English, technical-looking error surfaced by the AI Agent (rule 5's "never fabricate, relay the real error" leaves it no better option) rather than a clean re-offer of other times — safe (no double-booking, ever), just clunky UX for this specific edge case. Not fixed as of 2026-09-14; a proper fix would have `Respond Booked` re-run availability and attach `otherAvailableSlots` on this error path too, but the odds of two real users racing the exact same slot to the second are low enough that this was deprioritized rather than fixed immediately.
  - **Known residual edge case, deliberately fixed too**: booking **"both"** executives creates 2 events (one per calendar) in one request; if another request races for *just one* of those two calendars at the same instant, the "both" request could previously end up with one calendar booked and the other rejected — a half-completed booking reported as full success. Fixed by inserting a new Code node **`Rollback Partial Booking`** between `Create Event` and `Respond Booked` (Mode: "Run Once for All Items"): if some calendars in the batch succeeded and others got a `409`, it calls `this.helpers.httpRequestWithAuthentication.call(this, 'googleCalendarOAuth2Api', { method: 'DELETE', ... })` to delete the succeeded one(s) (matching each item back to its `targetCalendarId` via `$('Split Bookings').all()` by index, the same pattern used elsewhere in this workflow), then reports the whole booking as failed rather than half-done. `Respond Booked`'s final version checks for a single consolidated error item from this node.
- **Auto-invite by address book was silently a no-op since it was built, until fixed 2026-09-14** — both matching nodes (`Build FreeBusy Request (Book Guard)` for single-day, `Compute Multi Availability & Decide` for multi-day) read the `AddressBook` sheet via `$('Read Address Book').all()` and looked up each participant with `r['ชื่อเล่น']` / `matches[0]['อีเมล']` (Thai keys), but the sheet's actual header row is English (`Nickname`, `Email` — confirmed by opening the sheet directly). `r['ชื่อเล่น']` is always `undefined` against real row objects, so the match list was always empty and `autoInvitedNames` came back `[]` on every booking, no matter how many valid AddressBook entries existed — no error was ever thrown, it just silently invited nobody. Caught by testing a real booking with two AddressBook-listed participants ("หยก", "วุ่นวาย") and noticing neither got the "ส่งคำเชิญให้..." confirmation line nor an `attendees` entry in the node's own output JSON. **Fix**: changed both nodes' lookups to `r['Nickname']` / `matches[0]['Email']`. Confirmed working live on both the single-day and multi-day paths after the fix (2026-09-14). **Takeaway: when a Code node's object-key string literals are in Thai, double check them against the actual sheet header row rather than assuming — a silent-no-match bug like this throws no error and easily hides behind "well the feature is there in the code."**

If the user starts describing a new meeting (new date/topic), any earlier "send an invite" instruction from a previous meeting in that conversation must be treated as no longer applicable; inviting someone to a past-discussed booking requires asking which meeting (date/time) is meant, then handling it as a separate edit request.
- **Known unfixed limitation**: rescheduling a meeting to the **exact same date+time** as the one being replaced (e.g. "add a participant to my existing Monday 12:30 meeting, keep the time") self-conflicts, because the reschedule flow always books the new slot *before* cancelling the old one — the old event is still on the calendar when the availability check runs, so it looks "taken" by itself. As of the `Respond Conflict` fix this at least fails cleanly with an "already booked, pick another time" message (it used to crash the node) rather than silently doing nothing, but the underlying request (pure participant-list edit, no real time change) still can't succeed this way. Considered a proper fix (a dedicated "update event in place" action via Calendar `PATCH` instead of book+cancel, or reordering to cancel-then-book only when old/new date+time are identical) but the user decided to scrap that work and leave this limitation as-is for now.
  - Original design (for reference): look up each named participant in the `AddressBook` sheet; exactly one match → invite automatically; no match → stay silent; multiple matches (ambiguous nickname) → block the booking and have the AI ask which one / for the email, then retry with `inviteEmails` filled in. Gated on `source !== 'website'` so the website's behavior never changes.

## Full-system audit 2026-10-21 (against the 2026-10-21 export) — status of each finding

Paste-ready guides live in the project root as `fix_*.txt` (gitignored). Test bookings were made straight at the webhook with `callerName: "เทสระบบ"`, `company: "TEST"`, no email, on far-future dates, then cancelled. **Final state verified against the 2026-10-22 12:12 export (71 nodes)**: every new Code node matches the intended source byte-for-byte, both `Probe Event ID*` nodes have Never Error + On Error Continue, both `Log Booking*` nodes are Map Automatically + On Error Continue, `Respond Conflict` has the single-`=` body, and all wiring is as described below. Both racers compute the same k, so atomicity is preserved. The website then throws its generic "เกิดข้อผิดพลาดในระบบ…" instead of "ช่วงเวลานี้เพิ่งถูกจองไปแล้ว" + slot refresh, and the Discord tool gets an empty result.
